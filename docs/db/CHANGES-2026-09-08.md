# Executed live in Supabase — 2026-09-08

Applied to project `dkdxefzhttkmjhdbkvqn` as migration
`actblue_sync_runs_and_refunds`. Nothing here needs re-running; the same
statements are committed as
`supabase/migrations/20260908000000_actblue_sync_runs_and_refunds.sql`, and
that file's header explains each change. Context: `docs/actblue-sync.md`.

## What landed

- On `founding_members`: `phone`, `address1`, `zip`, `refcode`,
  `actblue_donor_id`, `refunded_at`, `recurring_cancelled_at`, plus indexes on
  `actblue_receipt_id` and `email`.
- On `donors`: `fee_cents`, `recurrence_number`, `kind`, `actblue_donor_id`,
  `refunded_at`, `recurring_cancelled_at`, plus the same two indexes.
- `founding_member_tiers.actblue_url`, filled for the five tiers. The
  2026-04-27 migration that added it never reached production, so
  `/api/founding-member-tiers` had been answering 500 and the tier cards on
  `/founding-members` fell back to static markup. Verified 200 after applying;
  the cards are now ActBlue links.
- `donor_sync_founding_member()` (the founding → donors fan-out) copies the
  new fields. Refund and cancellation stamps mirror the founding row; the
  address-style fields fill blanks only, so values the 2026-08-06 rollup
  reconciliation filled on `donors` are never blanked.
- `fill_oh_county()` (trigger on both tables) falls back from the city lookup
  to `county_for_zip(zip)`, and only accepts a value present in
  `ohio_counties`, so the founding county check constraint cannot reject an
  insert.
- `founding_members_progress()` and `founding_members_public` exclude rows
  with `refunded_at`; `contacts_directory`'s giving rollup ignores refunded
  gifts. No row carried a refund at apply time, so nothing public changed:
  the roster still shows 179 and the progress RPC still returns 179.
- New table `public.actblue_sync_runs` (one row per sync run) with RLS:
  select for `authenticated` via `has_permission('donors','read')`, all for
  `service_role`; `anon` revoked.

## Verified after applying

- A rolled-back test insert on both tables: county filled from ZIP (Portage
  for a `zip_lookup` ZIP with no city), the fan-out row carried phone, ZIP,
  refcode and `recurrence_number = 1`, and the founding number sequence
  advanced normally (the transaction was rolled back, so 179 remains the high
  mark).
- Security advisors: no new findings. `founding_members_public` remains a
  definer view on purpose (the public roster depends on it; see
  `advisors-2026-08-06.md`).

## Not done, on purpose

- Historical `contributed_at` values were left alone. A dry run matched 145
  existing founding rows to their ActBlue payments and the stored timestamps
  agree with the Eastern-to-UTC conversion the sync now performs, so no
  correction was needed (one row is ~26 hours off and was entered by hand).
- `supabase/migrations/20260511000000_actblue_report_backfill.sql` and
  `20260427000000_ohio_zip_county.sql` remain unapplied in production, as
  before. The ZIP → county crosswalk would let `fill_oh_county()` and
  `contacts_fill_geo()` cover every Ohio ZIP instead of the 45 in
  `zip_lookup`; that is a separate decision.
