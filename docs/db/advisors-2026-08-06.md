## Remaining, with reasoning — do not bulk-fix

### `security_definer_view` (ERROR x11)

These views read RLS-locked tables on purpose so a limited surface is
queryable by the public site or by admins without per-table grants. Converting
them to `security_invoker` breaks their consumers unless matching SELECT
policies are added first. Per-view calls:

- **Keep definer (public site depends on it):** `founding_members_public`
  (donor roster), `legislator_scorecard`, `public_endorsements`,
  `pride_events_public`, `v_current_methodology`. These are the curated
  public read paths; the base tables must stay locked.
- **Candidates for invoker + admin policy (admin-only consumers):**
  `volunteers_admin`, `submissions_inbox`, `intern_applications_admin`,
  `email_bounce_review_queue`, `v_committee_eligibility`, `v_scorable_events`.
  Each needs its consumer page checked, then `alter view ... set
  (security_invoker = true)` plus `is_admin()` SELECT policies on any base
  table not already covered. Do these one at a time with the page open.

### `rls_enabled_no_policy` (INFO x7)

All in the `archive` schema — the 2026-08-06 snapshots are locked down by
design (no API access path). Leave as is.

### `anon/authenticated_security_definer_function_executable` (WARN x45)

Mostly intentional (`has_permission`, `is_admin`, `county_for_zip`, the
trigger bodies). Worth a later pass to `revoke execute ... from anon` on the
admin-only ones (`publish_scorecard*`, `merge_contacts`,
`contacts_possible_duplicates` already restrict; `submit_board_retreat` needs
anon by design). Low urgency: each function gates internally or exposes
non-sensitive lookups.

### One-click dashboard items

- `auth_leaked_password_protection`: enable "Leaked password protection" in
  Auth settings (dashboard toggle, no code change).
- `extension_in_public` (`citext`, `pg_trgm`): standard advice is a dedicated
  schema; moving them touches every column type reference. Skip unless a
  migration window opens.

## Known accepted risks (from the branch's adversarial review)

- **users:manage_users can self-escalate to super_admin.** Every write surface
  for roles (admin_users, admin_user_roles, admin_roles, role_permissions)
  gates on `has_permission('users','manage_users')`, so any holder can grant
  themselves the super_admin role. Today only super_admin carries
  manage_users, making this moot; if manage_users is ever delegated, move the
  role-sync into a SECURITY DEFINER RPC that refuses super_admin grants from
  non-super-admins.
- **endorsement_reviews self-vote pins only reviewer_email.** A read-only
  reviewer could write a misleading reviewer_name/reviewer_user_id on their
  own row. All reviewers are board members and every vote also lands in
  endorsement_activity with the JWT-derived actor_email; tighten with a
  WITH CHECK subquery against admin_users if it ever matters.
- **Pre-cutover admin sessions require one re-login.** Sessions were
  localStorage-only before the cookie cutover; the middleware cannot see
  them, so each admin signs in once after deploy. The storage adapter still
  migrates localStorage sessions in fail-open (env-less) environments.
